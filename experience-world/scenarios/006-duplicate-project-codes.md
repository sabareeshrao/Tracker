| Database ID | Project Code | Project Name |
|---|---|---|

**Mentor:** Excellent observation.

### 🦊 Step 2 — Why can two rows have the same project code?

**Mentor:** Imagine our application gives every inserted record its own numeric ID.

```text id="pcd0gn"
Database ID : 1
Project Code: PRJ-101
```

If we insert another record, MySQL can generate another database ID.

```text id="ax6628"
Database ID : 2
Project Code: PRJ-101
```

**Student:** So the database thinks they are different because their IDs are different?

**Mentor:** They are two different database rows. But according to our business rule, both represent the same mapping project.

Let's separate the two ideas.

| Database ID | Project Code |
|---|---|
| Generated by the database | Provided or assigned by the business |
| Identifies one database row | Identifies one business project |
| Example: `1` | Example: `PRJ-101` |
| Usually our primary key | Can have a separate unique constraint |

**Student:** So which one should be unique?

**Mentor:** In our example, **both**.

Every row has a unique database ID.

And our business rule says every mapping project must have a unique project code.

**Student:** What if two genuinely different projects happen to share a name?

**Mentor:** Good question!

Two customers might both have projects named *Hyderabad Mapping*.

So we shouldn't automatically treat the project name as the unique identity.

We need a business-approved rule that specifies what makes one project different from another.

For our scenario, that rule is:

**One project code represents one project.**

**Mentor:** Exactly.

**Student:** Does that mean we might still create duplicates?

**Mentor:** Yes, if the database doesn't enforce uniqueness.

This is called a **race condition**.

```text id="0vbzv6"
Time        Employee A          Employee B
-------------------------------------------------
10:00:01    Check PRJ-201
            Not found

10:00:02                        Check PRJ-201
                                Not found

10:00:03    INSERT PRJ-201

10:00:04                        INSERT PRJ-201
```

**Student:** So checking from Java isn't enough?

**Mentor:** Correct!

A check can make error messages friendlier, but it isn't sufficient to guarantee uniqueness when concurrent requests are possible.

We need a rule that MySQL itself enforces.

### 🐨 Step 6 — Introduce the UNIQUE constraint

**Mentor:** Remember that our table has two identities.

```text id="d8fg7b"
Database ID  → id
Business ID  → project_code
```

Our database ID can be the primary key.

And we can put a unique constraint on `project_code`.

For example, an illustrative schema could look like this:

```sql id="np1mnq"
CREATE TABLE projects (

    id BIGINT AUTO_INCREMENT PRIMARY KEY,

    project_code VARCHAR(40) NOT NULL,

    name VARCHAR(200) NOT NULL,

    status VARCHAR(30) NOT NULL,

    archived BOOLEAN NOT NULL DEFAULT FALSE,

    CONSTRAINT uq_project_code
        UNIQUE (project_code)
);
```

**Student:** What does `UNIQUE (project_code)` do?

**Mentor:** It tells MySQL that two rows must not have the same project code, according to the column's comparison rules.

Now imagine both employees try again.

```text id="se833u"
Employee A                   Employee B
    |                            |
    | INSERT PRJ-201             | INSERT PRJ-201
    ↓                            ↓
             MySQL
               |
        UNIQUE constraint
               |
         /-----------\
        /             \
   One INSERT      Other INSERT
    succeeds        rejected
```

**Student:** So even if Java allows both requests to reach MySQL, the database prevents two identical project codes?

**Mentor:** Exactly. 🐯

That's our most important lesson today.

**Application checks help the user. Database constraints protect the data.**

*Note:* This schema illustrates the business-code column added to our earlier project model. In a real existing database, we'd migrate and backfill that column carefully rather than simply replacing the table.

### 🦊 Step 7 — What error does MySQL produce?

**Student:** What happens to the request that loses the race?

**Mentor:** MySQL rejects the conflicting insert.

For an ordinary duplicate-key violation, MySQL reports error code `1062`.

JDBC reports the database failure through an `SQLException`.

**Student:** So does the employee see a huge SQL exception?

**Mentor:** They shouldn't.

We want the application to translate a known database conflict into a meaningful response.

For example:

```text id="axrtg1"
Employee submits PRJ-201
              ↓
MySQL finds duplicate code
              ↓
JDBC reports duplicate-key error
              ↓
Java handles that specific error
              ↓
HTTP 409 Conflict
              ↓
"Project code already exists"
```

**Student:** Why 409?

**Mentor:** HTTP `409 Conflict` can communicate that the request conflicts with the current resource state.

The submitted project code is already taken.

But we must be careful not to treat every SQL exception as a duplicate.

A database connection failure is a different problem.

### 🐯 Step 8 — Our new Java implementation

**Student:** Could you show me the code connecting the form to MySQL?

**Mentor:** Sure.

We already know the basic Servlet and JDBC flow from Day 2, so today we'll focus only on what's new: project-code uniqueness and handling the duplicate-key result.

Assume the table from our educational schema exists, and `projectCode` and `projectName` are submitted form fields.

```java id="t83nww"
@WebServlet("/projects/create")
public class CreateProjectServlet extends HttpServlet {

    @Override
    protected void doPost(
            HttpServletRequest request,
            HttpServletResponse response)
            throws IOException, ServletException {

        String rawCode = request.getParameter("projectCode");
        String rawName = request.getParameter("projectName");

        if (rawCode == null || rawName == null
                || rawCode.isBlank() || rawName.isBlank()) {

            response.sendError(400, "Project details are required");
            return;
        }

        String projectCode =
                rawCode.trim().toUpperCase(Locale.ROOT);

        String projectName = rawName.trim();

        String sql = """
            INSERT INTO projects
                (project_code, name, status)
            VALUES (?, ?, ?)
            """;

        try (
            Connection connection = DriverManager.getConnection(
                System.getenv("DB_URL"),
                System.getenv("DB_USER"),
                System.getenv("DB_PASSWORD")
            );

            PreparedStatement statement =
                connection.prepareStatement(
                    sql,
                    Statement.RETURN_GENERATED_KEYS
                )
        ) {

            statement.setString(1, projectCode);
            statement.setString(2, projectName);
            statement.setString(3, "CREATED");

            statement.executeUpdate();

            try (ResultSet keys = statement.getGeneratedKeys()) {

                if (!keys.next()) {
                    throw new ServletException(
                        "Database did not return a project ID"
                    );
                }

                long newId = keys.getLong(1);

                response.sendRedirect(
                    request.getContextPath()
                    + "/projects?id="
                    + newId
                );
            }

        } catch (SQLException ex) {

            if (ex.getErrorCode() == 1062) {
                response.sendError(
                    409,
                    "Project code already exists"
                );
                return;
            }

            throw new ServletException(
                "Unable to create project", ex
            );
        }
    }
}
```

<caption>Illustrative MySQL-specific example. It assumes proper JDBC configuration, imports, a generated primary key, and project-code uniqueness. In a real application, check which unique constraint failed, validate field lengths and code formats, and apply authentication, authorization, and CSRF protection. Only the known duplicate-key error is mapped to 409.</caption>

**Mentor:** Correct.

**Student:** And `getGeneratedKeys()` gets the new database ID?

### 🦁 Step 10 — The unexpected retry problem

**Mentor:** Now let's examine an even more interesting situation.

An employee clicks Save.

MySQL successfully inserts `PRJ-301`.

But before the browser receives the response, the network connection drops.

```text id="hh1ex0"
Browser sends PRJ-301
          ↓
Java Servlet receives request
          ↓
MySQL INSERT succeeds ✅
          ↓
Network connection fails ❌
          ↓
Employee sees no success response
```

**Student:** But the project was saved!

**Mentor:** Exactly.

The employee doesn't know that.

So they click Save again.

**Student:** Then the second request finds the duplicate and returns 409.

**Mentor:** Correct, with the simple implementation we've written.

**Student:** But the employee might think the original project wasn't created.

**Mentor:** Excellent observation!

This is an important distinction:

**A duplicate caused by a genuinely new request is not always the same as a retry of a previously successful request.**

**Student:** How can the application know the difference?

**Mentor:** One common technique is an **idempotency key**.

Imagine the browser creates an identifier for one logical Save operation:

```text id="en2ryp"
Request attempt 1
Idempotency Key: SAVE-ABC-123

Request attempt 2 (retry)
Idempotency Key: SAVE-ABC-123
```

The server can use a reliably stored record of that key and its outcome to recognize a repeated attempt.

**Student:** So the retry can receive the original result instead of creating another project?

**Mentor:** Exactly, when the idempotency mechanism has been designed and stored correctly.

But notice: a `UNIQUE(project_code)` constraint alone doesn't implement the full idempotency-key workflow.

It prevents duplicate business codes. An idempotency mechanism additionally helps identify repeated attempts at the *same logical operation*.

We'll build that mechanism more deeply when we study retries and reliable processing.
